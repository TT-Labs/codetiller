# Fixing a bug: red command first

1. **Before reading code to form a theory, get one command that goes red on this bug.** Usually a new test in the existing test file for that area, asserting the exact symptom from the issue (the reported input, the reported wrong output or error). Run it and see it fail for the reported reason, not for a typo or an import error.
2. **If the issue describes several cases, cover each one** in that test. The red test is your definition of done; a case you did not encode is a case you will not fix.
3. **Keep it fast and narrow**: one test file, filtered by name, seconds per run.
4. **Then find the cause.** If the first idea does not turn the test green, write down two or three alternative causes and what each predicts, and test one change at a time. Do not stack speculative edits.
5. **Fix at the cause, not at the symptom.** Check whether the same code path has siblings (other implementations, other entry points) with the same defect and cover them with the same test.
6. **Done means**: the red test is green, the existing tests of every file you touched are green, and any debug output you added is removed.

If you cannot make any command go red, say so in your final message and state what you tried, instead of shipping an unverified fix.
